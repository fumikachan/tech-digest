# API と DynamoDB の設計

Phase 3 で作る API（API Gateway + Lambda）と DynamoDB のテーブルの設計。
DynamoDB は SQL のように後から自由に絞り込めないので、先に「どんな読み書きをするか」を決め、それに合わせてキーを作る。

## 前提

- 記事は 1 日約 400 件（2026-10-12 の実績: Qiita 349、はてな 31、Zenn 24）。1 件は 0.3〜0.6 KB
- 1 年で約 15 万件・60 MB 程度（無料枠の 25 GB に十分収まる）
- 今の SQLite / PostgreSQL と同じ決まりを守る
  - 記事は (source, url) で 1 件
  - `digest_date` は初めて載った日で、後から取得しても変えない

## アクセスパターン

| # | 使う場所 | 読み書き | 内容 |
|---|---|---|---|
| W1 | 収集バッチ | 書き | 記事を保存する。新しい記事なら今日の日付を付け、既にある記事ならタイトル・スコアなどだけ更新する |
| W2 | 収集バッチ | 書き | その日の取得元ごとの件数を記録する（アーカイブ用） |
| R1 | トップ・アーカイブ | 読み | 日付の一覧（新しい順）と、取得元ごとの件数 |
| R2 | 日付のページ | 読み | ある日の記事をすべて |
| R3 | 検索 | 読み | 直近 30 日の記事からキーワードで探す |

## テーブル

テーブルは 1 つ（`tech-digest`）にし、記事と日付の 2 種類のアイテムを入れる。
キーの名前は `PK` / `SK` のように中身に依存しない名前にして、アイテムの種類ごとに使い方を変える（シングルテーブル設計）。

### 記事のアイテム

| 属性 | 例 | 説明 |
|---|---|---|
| `PK` | `ARTICLE#qiita#https://qiita.com/foo/items/123` | パーティションキー。(source, url) で 1 件になる |
| `SK` | `ARTICLE` | ソートキー（記事では固定値） |
| `GSI1PK` | `DAY#2026-10-12` | GSI1 のパーティションキー。初めて載った日 |
| `GSI1SK` | `qiita#2026-10-11T23:10:00+00:00` | GSI1 のソートキー。取得元 → 公開日時の順に並ぶ |
| `source`, `url`, `title`, `published_at`, `digest_date`, `updated_at` | | 今の DB と同じ |
| `author`, `score` | | 値がないときは属性ごと持たない |
| `tags` | `["Python", "AWS"]` | DynamoDB のリスト型で持つ（今の DB のような JSON 文字列にはしない） |

### 日付のアイテム

| 属性 | 例 | 説明 |
|---|---|---|
| `PK` | `DAYS` | すべての日付を 1 つのパーティションにまとめる（1 年で 365 件なので小さい） |
| `SK` | `2026-10-12` | 日付。文字列の順に並べると日付の順になる |
| `counts` | `{"qiita": 349, "zenn": 24, "hatena": 31}` | 取得元ごとの件数 |
| `updated_at` | | |

### GSI1（日付から記事を引くためのインデックス）

- パーティションキー `GSI1PK`、ソートキー `GSI1SK`
- 射影は `ALL`（日付のページで記事のすべての属性を使うため）

### 読み書きの方法

| # | 操作 |
|---|---|
| W1 | 記事ごとに `UpdateItem`。`digest_date` と `GSI1PK` / `GSI1SK` は `if_not_exists()` で「まだないときだけ」入れる。これで「初めて載った日は変えない」が 1 回の書き込みで守れる |
| W2 | 保存のあとに GSI1 を今日の日付で `Query` して件数を数え、日付のアイテムを `PutItem` で上書きする（何度実行しても同じ結果になる） |
| R1 | `Query PK = "DAYS"`（新しい順） |
| R2 | GSI1 を `Query GSI1PK = "DAY#2026-10-12"`。並べ替え（スコア順・新しい順）は API で行う |
| R3 | R2 を直近 30 日分繰り返し、Lambda の中でキーワードで絞り込む |

`Scan`（テーブル全体を読む操作）は使わない。

#### 補足

- `BatchWriteItem` は条件付きの更新ができないので、W1 は 1 件ずつ `UpdateItem` する。1 日 400 回程度なので問題ない
- `Query` は 1 回で最大 1 MB までしか返さない。続きは `LastEvaluatedKey` で取る（1 日分は約 160 KB なので普段は 1 回で済むが、ページ送りは必ず実装する）
- 属性名が DynamoDB の予約語と重ならないよう、式の中では `#name` の形（ExpressionAttributeNames）で書く

### 費用の見積もり

1 日分の記事を読むと、約 20 読み込みユニットを使う（結果整合性の読み込みで、4 KB ごとに 0.5）。

| 操作 | 1 回あたり | 備考 |
|---|---|---|
| 収集バッチ | 約 800 書き込みユニット | 記事 400 件 × (テーブル + GSI1) |
| 日付のページ | 約 20 読み込みユニット | |
| 検索 | 約 600 読み込みユニット | 30 日分。いちばん重い |

- **オンデマンドモード**: 使った分だけ払う。検索 1 回で 0.01 円程度
- **プロビジョンドモード**: 無料枠（読み・書きそれぞれ毎秒 25 ユニット）の中なら 0 円
  - 使い残した分を最大 5 分ぶん貯めておいて一時的に超えられる（バースト）。それでも検索が続くと上限を超えてエラー（スロットリング）になる
  - 収集バッチは約 30 秒に分けて書き込むことになる（boto3 が自動で再試行する）

容量モードは AWS にテーブルを作る前に決める（PLAN の未決定事項）。

## API

ベースの URL は API Gateway の HTTP API。読み取りだけで、認証はなし。

| メソッドとパス | 返すもの | 使う DynamoDB の操作 |
|---|---|---|
| `GET /sources` | 取得元の一覧（name, title, description, score_unit） | なし（コードの `SOURCES`） |
| `GET /days` | 日付の一覧（新しい順）と取得元ごとの件数 | R1 |
| `GET /days/{date}` | その日の記事 | R2 |
| `GET /search?q=...&source=...&sort=score\|date` | 直近 30 日の検索結果（最大 100 件） | R3 |

### レスポンスの例

`GET /days/2026-10-12`

```json
{
  "date": "2026-10-12",
  "articles": [
    {
      "source": "qiita",
      "url": "https://qiita.com/foo/items/123",
      "title": "…",
      "author": "foo",
      "score": 120,
      "tags": ["Python", "AWS"],
      "published_at": "2026-10-11T23:10:00+00:00"
    }
  ]
}
```

- `url` は `render.safe_url` を通す。http(s) 以外は `null` にする（今のサイトと同じ）
- 記事の並び順はスコアの高い順（同じなら新しい順）

### エラー

| 状況 | ステータス |
|---|---|
| 日付やパラメータの形式がおかしい（`q` が 100 文字を超える、など） | 400 |
| その日のダイジェストがない | 404 |
| それ以外 | 500（中身はログにだけ出し、レスポンスには書かない） |

### その他

- **CORS**: AWS では API Gateway の CORS 設定で、サイトのオリジンだけ許可する。ローカルでは Vite の開発サーバーのプロキシ経由で呼ぶので、CORS は要らない
- **キャッシュ**: 過去の日付は内容が変わらないので `Cache-Control` を付ける（Phase 5 で CloudFront を前に置いたときに効く）
- **ハンドラー**: フレームワークは使わず、API Gateway のイベント（ペイロード形式 2.0）を直接受け取る。処理の中身はハンドラーの外の関数に分け、テストとローカルの開発用サーバーから同じ関数を呼ぶ

## ローカルでの動かし方

| 本番 | ローカル | テスト（pytest） |
|---|---|---|
| DynamoDB | DynamoDB Local（compose に追加） | moto |
| API Gateway + Lambda | ハンドラーを包む開発用サーバー | ハンドラーに偽のイベントを渡す |
| SPA の配信 | Vite の開発サーバー | — |

- 接続先は環境変数で切り替える。`DYNAMODB_TABLE` があれば DynamoDB を使い、`DYNAMODB_ENDPOINT_URL` があればその URL（DynamoDB Local）につなぐ
- テーブルを作るのは、ローカルではコマンドで行い、AWS では Terraform（Phase 3 では手作業）で行う。アプリの IAM ロールにはテーブルを作る権限を渡さない

## 検討した別の案

- **日付をパーティションキーにする**（`PK = DAY#日付`、`SK = source#url`）
  - 日付で引くのに GSI が要らない
  - ただし「この記事は前に載ったか」を調べるのに、別のアイテムをもう 1 つ書く必要がある
  - そのため、`if_not_exists()` で 1 回の書き込みで済む今の案にした
- **テーブルを 2 つに分ける**（articles と days）
  - 分かりやすい
  - ただし、DynamoDB でよく使われるシングルテーブル設計を学ぶ機会がなくなる
  - Terraform で管理するものも増える
